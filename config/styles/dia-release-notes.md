# Dia Weekly 风格指南

版本：初版，2026-10-22。依据：[来源与逐篇观察](../feed/dia/source-notes.md)。研究覆盖 9 篇正文样本、1 篇部分可读页面；不是全站统计。本文的规则是迁移写作建议，不能当作 Dia 内部编辑规范或效果实验结论。

## 核心：把一次更新写成工作中可感知的变化

起稿前回答：谁在什么时候，原来要做什么，现在能怎么做，哪些限制仍需知道？用户能想象操作，才有理由在意功能名。

例如 S08 写打开 PR 之前的判断困难，再写悬停动作；S03 把会议材料管理沿会议进程展开；S09 用具体任务解释工具集成。共同点是把能力落实到工作行为。S02 的年度回顾、S10 的品牌说明表明，这并不是强制痛点开场公式。

## 选主线与分配篇幅

| 更新材料 | 推荐组织方式 | 来源线索 |
|---|---|---|
| 一个能改变工作方式的功能 | 一个场景 → 新动作 → 结果 → 必要操作信息；次要项短列 | S03、S08 |
| 多项工具或能力 | 按任务分节，每节给用途或可尝试输入 | S09 |
| 性能与稳定性 | 已知问题 → 有证据的原因与改动 → 改善范围 → 反馈方法 | S06 |
| 没有头条的小修 | 简短承认本周重点，按使用领域分组 | S01、S02 |
| 品牌与视觉 | 为什么投入 → 具体可见触点 → 有节制的感受描述 | S10 |

以上是编辑选项，不是必须凑齐的段落。重要设置或风险很长时，宁可单独写步骤或链接帮助页，不挤进一句宣传语。维护完整功能清单时，可用精选周刊配合完整 changelog；没有完整记录就不要虚构链接或宣称所有更新已列出。

## 七条可操作的写法

1. **标题先给动作、状态或结果。** 读者应知道与自己有什么关系。明确的组件名称也可作标题；别为了俏皮丢失可识别性。S08、S05。
2. **场景包含对象和时刻。** “更高效地协作”过于抽象；“回复邮件前，先确认这串讨论最后决定了什么”有明确任务。后者为教学改写，并非原文引用。S09。
3. **正文保留行为证据。** 写入口、触发条件、发生变化的对象，再解释好处。不要仅说“更智能、更顺畅”。S03、S07。
4. **技术细节解释用户会遇到的后果。** 若用户会担心同步冲突，就解释冲突；与判断和使用无关的实现过程可省略。S07。
5. **按事实限定承诺。** Beta、授权前提、已知问题、未完成工作不能被流畅表达抹掉。单一功能变化不能推出省时比例、零失败或适用于所有人。S01、S06、S07、S09。
6. **口语感来自对话和节奏。** 使用短段、自然动词、面向读者的表达；较长句可解释因果。不要机械规定每句字数，也不必每段加“你”。S06、S08。
7. **人情味有材料才写。** 署名、个人兴趣和小玩笑是样本中的可选手法。没有真实经历、采访或授权素材就省略。S04、S08、S10。

## 中文与品牌适配

先迁移信息选择和叙事逻辑，再决定语气。英文双关、俚语、连续破折号和夸张拼写不必逐字复制。中文用自然的动作句；避免“赋能、无缝、极致、颠覆”等没有信息的形容。

普通练习可用“你”；若为 CHITUBOX 实际发布，读取既有 `config/styles/chitubox-changelog.md`，保留其称谓、术语、语言与格式要求。它要求的三语、分类和条目格式属于该品牌现有规范，不是 Dia 风格。适合将 Dia 的场景写法用在导语及头条解说；用户若要更换正式模板，再按明确要求调整。

## 编辑时的诊断

| 看到的问题 | 修改动作 |
|---|---|
| 开头罗列五个功能名 | 找对读者最重要的一项，先讲使用时刻；其余留给正文 |
| “优化了性能，体验更顺畅” | 追问哪个动作、什么条件、有什么可核实变化；材料不足保留原事实并标待补 |
| 每项都写成一段故事 | 次要项压短；不把低影响修复包装成重大突破 |
| “再也不会失败” | 改回已证实的修复对象和范围 |
| 读完想试却找不到入口 | 补上事实已确认的入口或帮助链接 |
| 标题只有玩笑 | 加回对象或动作；玩笑可删 |
| 收尾突然出现团队故事 | 检查真实性与栏目需要；无材料直接结束 |

## 起稿提示词

根据已确认的产品材料写更新日志。先识别这次更新的主线与读者任务，选择适合的文章结构。用具体场景、操作变化与可验证的结果组织内容；保留前提、版本、平台、Beta 和已知限制。主次分明，语气亲切、坦率而克制。对缺失事实列待补项，不自行补写。仅在有真实素材且适合品牌时使用幽默、署名或个人栏目。按目标品牌格式输出；说明最重要的三项编辑决定。
