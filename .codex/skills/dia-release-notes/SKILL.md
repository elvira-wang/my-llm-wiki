# Dia-inspired Release Notes

在本知识库中，用有来源的 Dia Weekly 写法帮助用户写、改和学习产品更新日志。跟随用户语言。安装位置为项目 `.codex/skills/dia-release-notes/SKILL.md`，从该处向上三级定位项目根目录。

## 按需读取

- 起稿、改稿：读项目 `config/styles/dia-release-notes.md`。
- 解释来源：读 `config/feed/dia/source-notes.md`，引用 S 编号及原文 URL。它是抽样分析，不是全站存档；P01 仅部分文字可读。
- 教学：读 `outputs/tutorials/dia-release-notes-workshop.md`，选择适合用户水平的一个练习。
- 实际 CHITUBOX 发布：另读 `config/styles/chitubox-changelog.md`；品牌规范和当次要求决定称谓、格式及语言。不要自动用周刊结构替代正式模板。

## 事实与写法

Dia 只提供表达参考。目标产品事实来自用户明确给定的材料与项目 `wiki/`。不得把 Dia 的功能、性能、权限或设计者经历转给目标产品。指定外部材料尚未入 wiki 时，先按项目流程整理可复用知识，或仅使用用户明确提供的事实。

版本、入口、平台、Beta、兼容性和效果数据需有依据。缺失信息列待补，继续完成有依据的段落。虚构产品仅用于明确标注的教学示范。没有真实采访、署名或个人素材就省略生活栏目。

## 写稿

从材料识别读者、场景、原行为、新行为、入口和限制。按影响选主线：重大功能沿用户任务，多工具按用途，性能按问题与证据，零散修复按使用领域。没有明显痛点不强造痛点；单条修复可以直接短写。

标题帮助识别动作或结果，正文说明现在能做什么、如何开始。主次项不必等长。逐项核对承诺，不能用省时比例或绝对保证替代事实。

交付文案、必要待补项、三条以内编辑理由；用户只要成稿时省略非必要解释。保存到 `outputs/changelogs/` 的小写文件，按项目规则只提交本任务文件。

## 改稿

先指出最影响理解的两个问题，再按用户要求修订。关键处用“原句 → 修改 → 原因”解释，区分重排信息和补充事实。保留功能范围、前提和不确定性。只评不改的请求不直接提供完整改稿。

## 教学

一次练一个能力：找场景、写行为变化、选主线、压缩次要项或控制承诺。先给小段材料与限制，让用户写；收到稿件后引用其具体句子点评，再给最小幅度修改与迁移练习。用户未要求示范时，不在练习开始前泄露完整答案。

检查事实准确、场景具体、变化可想象、层次清晰、语气合适。目标是用户掌握编辑判断，不能以“像 Dia”为理由掩盖事实不足或固定套用故事结构。
